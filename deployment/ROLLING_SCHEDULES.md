# Графики прокатов

Графики являются отдельным логическим набором данных внутри Corporate RAG. Они не добавляются в Qdrant и не смешиваются с корпусом обычных документов.

## Синхронизация

- штатный `corporate-rag-update.timer` запускается каждый час;
- перед обычным инкрементальным обновлением скрипт вызывает `rolling-sync`;
- сам XLSX скачивается не чаще одного раза в 24 часа;
- почасовой timer даёт автоматическую повторную попытку после временной сетевой ошибки;
- файл проверяется как ZIP/XLSX и открывается через `openpyxl(data_only=True)`;
- проверяются ожидаемые листы и минимальное число распознанных записей;
- при неизменном SHA-256 и той же версии нормализатора повторная обработка пропускается;
- новый SQLite-снимок полностью создаётся во временном каталоге и атомарно заменяет текущий только после успешной проверки;
- при любой ошибке пользователи продолжают работать с последней успешно обработанной версией.

Рабочие данные:

```text
/opt/corporate-rag/storage/rolling-schedules/
  current.sqlite3
  status.json
  snapshots/<sha256>.xlsx
```

Хранятся два последних исходных XLSX. Исходная таблица не изменяется.

## Поиск и ответы

Runtime сначала определяет, относится ли вопрос к плану производства. Обычный вопрос продолжает штатный путь Qdrant → reranker → LLM. Для вопроса о графике:

1. из текста извлекаются название агрегата/листа, номенклатура и дата или период;
2. backend выполняет точный SQL-поиск по нормализованному снимку;
3. LLM получает только найденные проверенные факты и не имеет права менять стан, дату или номенклатуру;
4. ответ или детерминированная таблица содержат только `Стан / площадка`, `Дата` и `Номенклатура`;
5. тоннаж, производительность, внутренние служебные поля и ссылки на исходную таблицу пользователю не выводятся;
6. без явной даты по умолчанию выбираются текущие и будущие записи;
7. близкие типоразмеры, например `57×3` и `57×3,5`, имеют разные канонические ключи и не смешиваются.

Запросы о плане или графике возвращают таблицу. До 25 записей показываются целиком; более длинные выборки разбиваются на страницы. Вопрос только о количестве возвращает число без таблицы.

Ошибки Excel (`#VALUE!`, `#REF!`, `#NAME?` и другие) не превращаются в производственные значения. Лист с повреждённым импортом получает статус `unavailable`; отсутствие результата на таком листе не считается подтверждённым отсутствием плана.

## Ручные команды

Принудительная загрузка независимо от 24-часового интервала:

```bash
cd /opt/corporate-rag/app
sudo docker compose -f deployment/compose.production.yml \
  --profile update run --rm rag-update \
  python -m corporate_rag_ingestion rolling-sync --force --json
```

Состояние активного снимка без записи:

```bash
sudo docker exec corporate-rag-api \
  python -m corporate_rag_ingestion rolling-status --json
```

Журнал и timer:

```bash
sudo journalctl -u corporate-rag-update.service --since today --no-pager
sudo systemctl list-timers corporate-rag-update.timer --no-pager
```

## Проверка после развёртывания

```bash
curl -sS http://127.0.0.1:8010/ready | python3 -m json.tool

curl -sS -N --max-time 60 \
  -X POST http://127.0.0.1:3001/api/answer/stream \
  -H 'Content-Type: application/json' \
  -d '{"question":"Когда планируется прокат трубы 57×3,5?"}'
```

Блок `rolling_schedules` в `/ready` носит диагностический характер. Отсутствие первого снимка не делает обычную базу знаний неготовой; пользователь получит честное сообщение только при вопросе о графике.

## Откат

Откат кода выполняется возвратом предыдущего каталога `app` и пересозданием `rag-api` и `rag-frontend` из прежних тегов. Каталог `storage/rolling-schedules` можно оставить: старая версия его не использует.

```bash
cd /opt/corporate-rag
rollback_stamp=$(date +%Y%m%d-%H%M%S)
sudo mv app "backups/app-failed-$rollback_stamp"
sudo cp -a backups/app-before-update-<timestamp> app
cd app
sudo docker compose -f deployment/compose.production.yml \
  up -d --force-recreate rag-api rag-frontend
```
